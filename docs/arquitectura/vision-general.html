Visión general de la arquitectura

El sistema tiene tres componentes de software que se comunican exclusivamente por HTTP. Ninguno conoce los detalles internos de los otros: solo el contrato de la API.

Decisiones de diseño

Cliente–servidor con un único estado central

El mensaje vive solo en el backend. Navegador y ESP32 son clientes que leen (y el navegador también escribe). Así no hay que sincronizar copias: quien quiera el valor actual, lo pide.

Polling en lugar de push

La ESP32 pregunta cada segundo (polling) en vez de que el servidor le avise (WebSocket, MQTT…). Es menos eficiente, pero:

  • La ESP32 no necesita aceptar conexiones entrantes (funciona aunque esté detrás de NAT o firewall).
  • El código es mínimo y fácil de razonar.
  • Si se pierde la red, no hay estado que recuperar: la siguiente petición simplemente funciona.

Coste: hasta 1 s de latencia y ~86 400 peticiones al día. Ver Flujo de datos y tiempos y alternativas en Extender el proyecto.

Dos representaciones del mismo recurso

El backend ofrece el mensaje como JSON (/mensaje) para el navegador y como texto plano (/mensaje/texto) para la ESP32. El texto plano evita tener que incluir una librería de JSON en el microcontrolador.

Estado en memoria

El mensaje es una variable global de Python. Es suficiente para un ejemplo didáctico, pero se pierde al reiniciar el contenedor y no escala a varios procesos. Ver cómo persistirlo.

Configuración fuera del código

Lo que depende del entorno (WiFi, IP) está en config.h, fuera del control de versiones. El frontend deduce la URL del backend a partir de window.location.hostname, así que funciona igual en localhost o desde un celular sin cambiar nada.
