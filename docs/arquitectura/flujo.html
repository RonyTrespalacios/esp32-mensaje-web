Cómo se mueve un mensaje desde que lo escribes hasta que la ESP32 lo imprime, y cuánto tarda cada parte.

Presupuesto de latencia

Tiempo desde que pulsas Guardar hasta ver el texto en el Monitor Serie:

TramoTiempo típicoComentario
PUT navegador → backend< 10 msMisma máquina.
Espera hasta el siguiente GET de la ESP320 – 1000 ms (media 500 ms)Domina la latencia. Depende de delay(1000).
GET ESP32 → backend → ESP3210 – 50 msAbrir TCP + HTTP sobre WiFi.
Serial a 115200 baud~2 ms~11 520 bytes/s.
Total≈ 0.05 – 1.1 s

Carga generada

ClientePeriodoPeticiones/horaPeticiones/día
ESP321 s3 60086 400

Para un servidor local esto es insignificante, pero muestra el coste del polling: casi todas las respuestas son iguales a la anterior. Con 100 ESP32 serían 100 peticiones por segundo solo para enterarse de que “nada cambió”.

Compromiso latencia ↔ tráfico

Bajar el delay a 200 ms reduce la latencia media a ~100 ms pero multiplica las peticiones por 5. Alternativas que eliminan el compromiso: long polling, WebSockets, Server-Sent Events o MQTT. Ver Extender el proyecto.

¿Por qué la ESP32 no se satura?

Cada iteración crea un HTTPClient, abre una conexión TCP, lee la respuesta y la cierra con http.end(). Como la respuesta es texto muy corto y la conexión se libera siempre, el uso de memoria es constante. Si olvidaras http.end() se agotarían los sockets en pocos minutos.
